# Boundary evidence record

Use the repository's existing record format. Keep current task state in its task authority,
not in another editable board. A useful technical receipt answers:

- Which contract version and production call path changed?
- Who owns mutable state, admission, cancellation, revisions and joining?
- Which provider implements platform authority, and how is it selected or rolled back?
- Which dependencies disappeared from the portable component?
- Which old assertions moved unchanged, which new refusal checks were added, and what remains real integration?
- What actual before/after timings were measured under the same conditions?
- Which internal, schema, helper, fixture and runtime changes widen or refuse qualification?
- Which source/artifact/provider identities and consumer closure bind each result?
- What remains unverified, and what is the next finite slice?

Separate correctness, elapsed budget and deployment/native acceptance. Counts and file hashes
help bind evidence; neither proves the boundary is complete. Avoid a manual "unrelated tests"
allowlist that cannot explain its dependencies or survive an injected regression.
