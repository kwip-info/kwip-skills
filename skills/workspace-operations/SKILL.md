# Workspace operations

Resolve the workspace inventory, owning repository, current working agreement and task record
before meaningful work. Confirm which repository owns code, company policy, current work state
and production operations. A folder name, old summary or issue title does not establish authority.

For a new initiative, identify its intended outcome, evidence of success, affected owners and
what current work it displaces. Shared capability work should improve existing operations or
products; do not turn a small request into another platform or service by default.

Use the existing task authority and record a bounded start checkpoint before implementation.
Keep status, next action and evidence current at meaningful milestones, waits and closure.
If no tracker is available, use the workspace's existing durable work record and disclose the
visibility gap; do not install a second project-management system merely to satisfy this skill.
An intermediate checkpoint does not complete an unfinished authorized assignment or require
the user to authorize the same remaining work again.

Resolve conflicting facts from the source that owns them:

- Product contracts and current source own implementation behavior.
- Actual provider observations own mutable deployment, billing and delivery state.
- The workspace inventory owns repository membership and ownership.
- The task system owns current work state; old notes retain historical evidence.

Keep these roles distinct when consolidating documentation. Prefer one maintained instruction
and links from its callers over repeated policy copies. Do not silently replace historical
evidence with a newer result or infer publication from a merged branch.

For workspace cleanup, inventory tracked/untracked changes and recovery first. Separate
retired source, regenerable output, user data and retained release evidence. Remove only the
authorized scope; moving or deleting a local folder does not retire its remote repository,
domain, hosted service or customer commitment. Keep compatibility aliases only while they
serve a verified caller and document the migration's rollback.

Put organization-specific paths, brands, budgets and access rules in a private adapter.
Preserve technical identities and production integrations until an authorized migration proves
cutover and rollback. Read access does not imply permission to send, deploy, publish or expand
agent access; resolve genuinely missing authorization at the actual consequential boundary.

Close with the delivered outcome, owning source, actual validation and remaining work. Preserve
explicit deferrals as searchable issues with impact, confidence, workaround and revisit trigger.
