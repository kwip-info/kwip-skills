# Bounded work tracking

Before substantive implementation, resolve the existing task authority, owner, authorized scope,
finite acceptance and current record. Bind the actual session if supported and emit a concise
start checkpoint. Do not create another tracker, service or editable status board without a need
and user direction. If access is unavailable, use the existing durable work record and disclose
the gap while continuing independently authorized work.

Update status, next action, review and evidence together at meaningful milestones, external waits,
verification and closure. Backlog is not implementation approval. A passing test count, exit code
or intermediate source checkpoint is not accepted scope completion. Preserve unmet parent criteria;
continue already-authorized remaining work without asking for the same permission again.

For finite long work, register only the process you own with the existing observer. Record a
coarse purpose, PID/start identity and real progress counters when available. Distinguish an owned
wrapper's known exit from a watched PID disappearing. Never scan unrelated user apps or terminate
one merely to make the tracker look clean. Use actual lifecycle signals where available and make
missing coverage visible; do not imply access to the agent's thoughts or unseen activity.

A quiet process is a possible stall, not a proven deadlock. An explicit provider queue or user wait
is different from silence. Progress files should change on real work, not a timer heartbeat that
masks stalls. Missing/reused PIDs, observer loss and an observation timeout do not establish success
or justify a duplicate build, upload or external write.

Filter at capture time. Store only bounded identifiers, lifecycle categories, counters, durations,
source/evidence references and short summaries. Keep prompts, tool arguments/results, credentials,
environment dumps, raw logs and datasets out of activity storage. Redacting a huge retained trace
later is too late. Keep detailed technical evidence in its own authorized store with bounded links.

Define retention and event limits for the observer independently of durable tickets and explicit
acceptance records. Do not silently purge human work history to control noisy automatic telemetry.
Derive overview boards from the same task records rather than maintaining conflicting card state.

At closure, join/stop task-owned helpers, reconcile acceptance and leave the requested review state.
Keep deferrals searchable with affected component/version, impact, confidence, evidence, workaround
and revisit trigger. Mark blocked only when a real dependency prevents useful work; do not keep
repeating an unchanged blocker or create a new task to lose it. Public publication of tracker data
or process traces needs separate authorization and privacy review.
